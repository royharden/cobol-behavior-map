# Declarative generation contract v1

This document owns the serialization seam for standalone admission generation. It creates no cases or expected answers. Generator source is standard-library-only, deterministic, independent of the product parser/shim, target <=300 lines (split small modules if needed). It must not execute recipes as code, import author plugins, call a model or derive expected outputs.

## Field table

UTF-8 JSON, duplicate object keys forbidden, no BOM/NaN/floats/unknown keys. `manifest_version` is integer 1 throughout these contracts. A field document contains exactly `manifest_version`, `program_id`, `source_sha256`, `record_width`, `fields`. IDs match `[a-z][a-z0-9_-]{0,63}`; hashes are lowercase 64-character hex. `record_width` is an integer 1..8192. `fields` is a nonempty ordered list, maximum 32 entries, describing only input-record elementary fields, never internal packed storage. Each entry has exactly:

| Key | Type and meaning |
|---|---|
| name | uppercase COBOL identifier, unique after folding |
| pic | canonical `X(n)`, `9(n)`, `S9(n)`, optionally numeric `V9(m)` |
| usage | literal `DISPLAY` for these external fields |
| sign | `none` for X/unsigned, `leading_separate` for signed numeric |
| offset | integer zero-based byte offset |
| width | positive integer bytes, n for X, n+m plus separate sign byte for numeric |
| scale | integer 0 for X/integer, m for decimal |

Fields are in increasing contiguous offset order starting at zero; final end equals record_width. No overlaps/gaps, implicit padding fields, inferred reordering or encoding conversions. Width/scale/sign must agree with PIC; total numeric digits <=8 and scale<=4. Output layout uses a separate field document bound to the same source; never feed output layouts to input generation by inference.

## Recipe and exact values

Recipe document keys: `manifest_version`, `corpus_version`, `family_id`, `program_id`, `task_id`, `partition`, `fields_sha256`, `scenario`, `records`, `boundaries`, `fill`, `collision_counter`. Partition is `loop` or `verification`; task IDs bind unchanged or changed originals through FAMILY.md. Scenario enum is exactly `missing|empty|records`. `records` is an ordered list of complete field-name mappings: no absent/extra/duplicate keys, max64. For missing/empty it must be []; records scenario needs 1..64 rows. No host file paths, expressions, Python, template substitution, implicit defaults, oracle observations or expected bytes in recipes.

Numeric mapping values are ASCII decimal strings with optional leading `-` only, at least one integer digit, optional decimal point and <=scale fractional digits; reject exponent/plus/comma/whitespace. Values must be representable without rounding; pad missing fractional digits with zeros. Preserve an explicit lexical negative zero for signed fields; unsigned negative values including `-0` are refused. Signed encoding is one `+`/`-` byte followed by zero-padded absolute unscaled digits. Unsigned encoding has digits only. X values are printable ASCII strings, length<=width, right-padded with spaces; embedded newline/CR/control bytes or overwidth refuse, never truncate. Semantic truncation/padding is exercised by program operations, not by malformed input encoding.

`boundaries` is an ordered list of `{id,field,kind,scenario,records}`. Field must exist (null only for eof); IDs unique. Each entry is one complete case with scenario/records under the same rules as the top-level case. Closed kind vocabulary: `zero`, `least_unit`, `field_max`, `result_max`, `result_max_plus_ulp`, `tie`, `non_tie`, `discarded_fraction`, `positive`, `negative`, `negative_zero`, `pivot_minus_one`, `pivot`, `pivot_plus_one`, `threshold_below`, `threshold`, `threshold_above`, `eof`. These tags document author intent, not computed compiler facts. Arithmetic-result overflow/tie boundaries describe *input* values that cause that intermediate/result; never encode an out-of-range input merely to meet a tag. Author supplies every field in complete row mappings. Generator must not infer arithmetic from COBOL. `eof` varies batch length or scenario; not a sentinel record.

`fill` has exactly `{algorithm,seed_material,target_count,max_records}`. Algorithm is `sha256-counter-v1`; target_count is 32 loop /128 verification; max_records is integer 1..64. Seed material is the JSON array of corpus_version, family_id, program_id, task_id, partition, exactly matching the enclosing identity. A change task uses its own task_id. No clock, Python hash(), host locale, OS randomness or unspecified random-library version. Canonical JSON below encodes this array; seed=SHA256(canonical array bytes). Define draw(c,r,f,b) as SHA256(seed || U64BE(c) || U32BE(r) || U32BE(f) || U32BE(b)); indices start at zero. Record count is 1+(unsigned-big-endian integer draw(c,0xffffffff,0xffffffff,0) modulo max_records). For a numeric field with d total digits let M=10^d-1; unsigned unscaled value is draw(c,r,f,0) modulo (M+1), signed is draw modulo (2*M+1) minus M; zero is positive in random fill. Format by scale with exact integer math. For X, concatenate draw(c,r,f,b) blocks for b=0,1,... and map the first width bytes independently to 32+(byte modulo95). This specifies a deterministic fill, not a uniform sampling claim. Consume the top-level case first, then boundary entries in order, then fill counters in order; no Cartesian expansion. Record missing/empty scenarios explicitly; fill emits records only.

`collision_counter` starts at nonnegative integer zero, the first fill counter. Increment it after every fill proposal, accepted or rejected. Consume loop before verification; verification receives the full loop hash exclusion set. Skip exact duplicate hashes (within or across task partitions), recording them, never perturb earlier admitted cases. An exclusion set cannot be guessed or omitted for verification. Reject a recipe if mandatory explicit top-level/boundary cases exceed target_count after deduplication, or if an explicitly required boundary collides across partitions; do not silently drop a required boundary. Seeded duplicate fill is replaced. At most100000 total fill proposals per task/partition; exhaustion returns `case_space_exhausted`. Candidate-independent oracle crash/timeout/nondeterminism is quarantined later with reason/hash/counter, replaced by the next deterministic candidate until full valid counts exist. Defined handled outcomes stay. Never reduce required counts or use candidate outcomes to replace data. Generation-only uniqueness is not oracle-valid admission.

Continuation is a deterministic candidate stream, not a rerun with a new seed. Visit explicit top-level/boundary cases once in order; equal hashes within one partition retain the first case and merge all boundary IDs onto it. Explicit different recipe labels never count as additional cases. Each fill proposal consumes one counter even if duplicate/quarantined. A generation receipt contains exactly `manifest_version`, `recipe_sha256`, `fields_sha256`, `partition`, `case_hashes`, `boundary_case_hashes`, `next_counter`, `fill_proposals_consumed`, `excluded_hashes_sha256`. case_hashes is admitted-in-order, boundary_case_hashes maps each explicit boundary ID to its case hash; excluded_hashes_sha256 hashes the canonical sorted unique exclusion list. Counter is U64 and may never wrap; reject `bad_seed` if the proposal cap would overflow. All scalar types are strict (bool is not an integer); corpus_version is a nonempty ASCII ID and other IDs/hashes obey the field-document rules.

The generator's source-only result supplies target_count unique candidates, not oracle-valid observations. Later admission resumes at next_counter with the same seed, prior accepted/seen hashes and quarantine hashes, recording each skip/replacement in the runner ledger. The100000 fill cap is cumulative across continuations. An explicit mandatory boundary that is oracle-invalid fails admission (do not silently replace its required semantic obligation); seeded invalid cases may be replaced. Finalize loop admission including all replacements before generating verification against its final exclusion set. If loop changes after verification was proposed, invalidate that unsealed verification proposal and regenerate it from its original seed against the final loop set, logging both versions. After sealing, no replacement is allowed without the plan's recorded reseal/revalidation rules. Neither generator nor runner may remove data in response to candidate performance.

## CaseBundle and hashing

In-memory CaseBundle: `{input_present: bool, records: ordered list[bytes]}`. Missing means false and []; empty means true and []; records means true and 1..64 exact-width records. No absent-file bundle may carry records. Scenario can be derived from this pair; source recipe retains its explicit scenario for audit. Do not add LF to a record value. File materialization concatenates each record followed by one ASCII LF, including the last record; present empty file is zero bytes; absent file is absent. Encoding and physical framing must be verified against the pinned LINE SEQUENTIAL runtime later.

Full-case preimage is ASCII `M10-CASE-v1` then byte 0x00, one byte 0x00/0x01 for presence, U32BE record count, then for each ordered record U32BE byte length followed by raw bytes. `case_sha256 = SHA256(preimage)`. Presence, record order, multiplicity and length are bound; no JSON/base64 implementation choice can alter this hash. Field/source/task hashes bind case identity in the enclosing manifest, not this byte hash; cross-partition disjointness compares this full-case byte hash for each task. Different task names cannot hide identical loop/verification bytes. Raw input file SHA256 is separate and cannot distinguish absent versus empty by itself.

Canonical JSON for documents/seed tuples: UTF-8, keys sorted lexicographically, separators comma/colon with no whitespace, no BOM/trailing newline, ensure_ascii=true, integers only, strings unchanged; reject duplicate keys before canonicalization. Artifact SHA256 sidecars hash actual stored bytes; canonical-document hashes are separately named. Do not silently replace one with the other. Record JSON output order cannot affect CaseBundle order.

## Typed generator failures

`manifest_version`, `unknown_key`, `duplicate_key`, `bad_identifier`, `bad_hash`, `bad_layout_or_sign`, `field_limit`, `bad_scenario`, `bad_record_count`, `missing_field`, `unknown_field`, `bad_value`, `value_out_of_range`, `negative_unsigned`, `bad_boundary`, `bad_seed`, `duplicate_case`, `partition_collision`, `case_space_exhausted`. Refuse malformed input before output writes; preserve no partial admitted partition. Diagnostics bind JSON pointer, recipe/fields hashes and stage. These are admission errors, never candidate divergences or successful cases.

## Freeze and later validation

DL2 owns implementation reconciliation; DL1 owns this spec; INT adjudicates seam changes before freeze. Freeze generator/field/recipe format and hashes after authorized dev probes, then builder/product wrapper imports that exact generator unchanged. Custodian and verifier exercise the same bytes independently. Deferred: encoding/negative-zero probes, deterministic repeated generation, collision/exhaustion and disjointness checks, layout/parser comparison, reachability checks and all compiler execution. This v1 document is construction-frozen on INT acceptance; it is not the post-probe instrument freeze.
